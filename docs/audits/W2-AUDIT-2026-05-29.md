## 1. Sumário executivo

**Recomendação: ❌ NO-GO para a Wave 3** (condicional — vira ✅ GO assim que R1
fechar).

### [AUD-W2-003] Cancel que promove a próxima sprint da fila não grava `displayed_at`

- **Severidade:** 🟠 Alto
- **Categoria:** Integração / Qualidade (interação cancel×fila×ack)
- **Componente:** C3 (Transversal C2/C3)
- **Item de backlog:** BL-C3-011, BL-C3-007, BL-C2-008
- **Local:** `apps/operator-agent/src/main/services/pollingService.ts:235-243`;
  wire em `apps/operator-agent/src/main/index.ts:277-285`
- **Descrição:** O ack inicial (`writeDisplayed`) é gravado **apenas** no wire
  `queueService.onNextSprint`. Quando um `cancel-*.json` fecha a sprint exibida
  e promove a próxima da fila, `processCancel` chama `overlay.showSprint(next)`
  **diretamente**, sem passar pelo `onNextSprint` e sem chamar `writeDisplayed`.
  Resultado: a sprint promovida aparece na tela do operador **sem ack
  `displayed_at`**.
- **Evidência:**

  ```ts
  // index.ts:277 — única origem de writeDisplayed
  queueLocal.onNextSprint((item) => {
    overlayLocal.showSprint(item, queueLocal.length());
    void ackLocal.writeDisplayed(item.payload); // <-- só aqui
    pillLocal.hide();
  });

  // pollingService.ts:235-243 — processCancel promove SEM writeDisplayed
  if (wasDisplayed && overlay !== undefined) {
    overlay.hide();
    const next = this.deps.queueService.peek();
    if (next !== null) {
      overlay.showSprint(next, this.deps.queueService.length()); // bypassa o wire
    }
  }
  ```

- **Impacto:** A tela de acompanhamento do líder (`AckTrackingService`) mostra a
  sprint promovida como **`nao_visto`** apesar de estar exibida. Se o operador
  clicar "Recebi", auto-cura para `confirmado` mas com `displayed_at` errado
  (`resolveDisplayedAt` cai no fallback `now`). Se o operador **não** der ack
  (auto-minimiza), o líder vê `nao_visto` **permanentemente** para uma sprint
  que foi exibida. Cenário: sprint A exibida + sprint B na fila + cancel de A.
- **Recomendação:** Em `processCancel`, ao promover `next`, gravar o
  `displayed_at` (chamar o mesmo caminho do `onNextSprint`, ou expor um
  `overlayService` callback que dispare `writeDisplayed`). Adicionar teste de
  interação cancel→próxima cobrindo o ack. Avaliar unificar a promoção de sprint
  num único ponto que sempre grava o ack inicial.
- **Esforço estimado:** S
- **Sessão de remediação sugerida:** R2

### [AUD-W2-004] CI não executa coverage em nenhum package — thresholds materializados não bloqueiam

- **Severidade:** 🟠 Alto
- **Categoria:** Qualidade / Regressão (infra)
- **Componente:** C0 / C8 (Transversal)
- **Item de backlog:** N/A (infra que sustenta BL-C8-008 e §7.7.1)
- **Local:** `.github/workflows/ci.yml:72-73`; `package.json:15-16`;
  `turbo.json:10-19`
- **Descrição:** O CI roda `pnpm test` (= `turbo test` = `vitest run` por
  package, **sem** `--coverage`). O script `test:coverage` existe mas **não é
  invocado pelo CI**. Logo, mesmo os thresholds materializados em
  contracts/fs-adapter/logger/leader/agent **só rodam localmente** se alguém
  rodar `test:coverage` à mão — em CI, **nenhuma cobertura é medida ou
  bloqueada**.
- **Evidência:**
  ```yaml
  # .github/workflows/ci.yml — não há step de coverage
  - name: Test
    run: pnpm test # → turbo test → vitest run (sem --coverage)
  ```
  ```jsonc
  // package.json
  "test": "turbo test",
  "test:coverage": "turbo test:coverage",   // existe, mas não usado no CI
  ```
  `grep coverage .github/workflows/ci.yml` → nenhuma ocorrência.
- **Impacto:** Contradiz a alegação de `CLAUDE.md` §7.7.1 ("build falha
  automaticamente se cobertura regredir"). Na prática, regressões de cobertura
  **não** quebram o CI hoje, em **nenhum** package. Compounda diretamente o
  AUD-W2-001 (sem este, BL-C8-008 não pode ser enforçado nem com threshold).
- **Recomendação:** Trocar o step de teste do CI para `pnpm test:coverage` (ou
  adicionar um step dedicado), garantindo que os thresholds por package
  efetivamente bloqueiem. Validar que o cache do Turbo (`outputs: coverage/**`)
  não mascare a checagem.
- **Esforço estimado:** S
- **Sessão de remediação sugerida:** R1 (junto com 001 — mesmo mecanismo)

- **Severidade:** 🟡 Médio
- **Categoria:** Completude / Integração (spec divergence)

  slot do overlay. O Agent agora exibe `sprint.meta` + a **string fixa

  `sprint.body_html` (calculado, substituído `{meta}` e sanitizado no Leader) é
  **gravado mas nunca renderizado** ao operador. No W1 o overlay exibia o body

  ```ts

  const SPRINT_UNIT = 'Artes'; // hardcoded — não existe no SprintPayload
  // SprintBody (127-146) usa sprint.meta + SPRINT_UNIT + SPRINT_LABEL; NUNCA sprint.body_html
  ```
- **Impacto:** (a) O líder customiza o título (BL-C2-006), mas o **corpo do
  aviso nunca chega à tela** — `body_html` é dado morto no caminho de exibição,
  divergindo de RF-17/RN-10. (b) A unidade "Artes" é assumida sempre — hardcoda
  o domínio ARTFLEXÍVEIS num produto chamado genericamente "Sprint Dispatcher".
  É uma decisão de design aprovada por Renan (imagem 'Hora do Rush!'),
  documentada como débito de schema (`kind`/`unit`), mas **não ratificada** como
  divergência de spec.
- **Recomendação:** Decisão de produto com Renan: (1) confirmar que o overlay
  deliberadamente não exibe `body_html` (e então marcar RF-17 como aplicável só
  à sanitização, não à exibição); (2) bump de `schema_version` para
  `kind`/`unit` no `SprintPayload` (remove o hardcode); (3) avaliar se
  `body_html` deve voltar ao overlay ou ser removido do contrato.
- **Esforço estimado:** M (envolve schema bump + propagação Leader/Agent)
- **Sessão de remediação sugerida:** R4 (precede decisão de Renan)

## 6. Integração — consistência de schema

### 6.1 Cancelamento (o mais crítico) — ✅ CONSISTENTE

Verificado **lado a lado**, não assumido. O campo de match é `sprint_id_ref` nos
quatro lados:

| Camada                  | Arquivo:linha                   | Campo usado                                                                                 |
| ----------------------- | ------------------------------- | ------------------------------------------------------------------------------------------- |
| C1 contrato             | `sprint-cancel.schema.ts:16`    | `sprint_id_ref: sprintIdSchema` (Anexo E)                                                   |

| C3 Agent (lê/age)       | `pollingService.ts:213,219,223` | `payload.sprint_id_ref` → match com `overlay...sprint.sprint_id` e `removeBySprintId`       |

Filename `cancel-<sprintId>.json` (`CANCEL_REGEX` em `filenames.ts:33`) e campo
interno `sprint_id_ref` são usados de forma coerente. **Sem divergência.** Fecha
sem ack (RN-06). Race de remoção de originais tratada (`FileNotFoundError`
silenciado em `cancel-store.ts:121-123`). **Ressalva:** o ack da sprint
promovida após cancel (AUD-W2-003).

### 6.2 Acks — ✅ CONSISTENTE

| Camada                             | Campos                                                                                                                                      |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| C1 (`sprint-ack.schema.ts`)        | `schema_version, sprint_id, user_id, hostname, displayed_at, acknowledged_at?, agent_version` (Anexo D)                                     |
| C3 escreve (`ackService.ts`)       | `writeDisplayed` → sem `acknowledged_at`; `writeAcknowledged` → adiciona `acknowledged_at`, preserva `displayed_at` original via re-leitura |
| C2 lê (`ackTrackingService.ts:80`) | 3 estados: sem ack=`nao_visto`; `displayed_at`=`visto`; `acknowledged_at`=`confirmado`                                                      |

Os campos escritos pelo Agent são exatamente os lidos pelo Leader. **Sem
divergência.** Ressalva indireta: AUD-W2-003 deixa a próxima sprint pós-cancel
sem `displayed_at`.

### 6.3 C9 → C3 (props do `<Overlay>`) — ✅

`type-check` limpo; o Agent passa
`title`/`body`/`onAcknowledge`/`acknowledgeLabel`/`autoCloseSeconds={0}`/`variant`
com tipos corretos. Nenhum `any`/`as` mascarando incompatibilidade no caminho.

### 6.4 Segurança (XSS) — ✅ SÓLIDA

`sanitizeBodyHtml` (`sanitize.ts`) usa whitelist estrita (`ALLOWED_TAGS` =
`b/i/br/p/h1/span`), `ALLOWED_ATTR: []`, `ALLOW_UNKNOWN_PROTOCOLS: false`,
`ALLOW_DATA_ATTR: false`, **sem** `USE_PROFILES` (ADR-014 respeitado). Por
construção, os vetores enumerados no prompt são neutralizados: `<img onerror>`,
`<svg onload>`, `<iframe>`, `<style>`, `<a href=javascript:>` — todas
tags/atributos fora da whitelist são removidos; aninhamento malformado
(`<scr<script>ipt>`) e entidades são tratados pelo parser do DOMPurify.
`<TextBlock>` re-sanitiza em todo render (defesa em profundidade, idempotente).
Cobertura C1 de sanitização: 100%. **Nenhum vetor passa.**
